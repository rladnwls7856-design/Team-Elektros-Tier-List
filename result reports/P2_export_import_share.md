## A. 무엇을 · 왜

**하나의 입구, 하나의 검증.** 파일 Import 와 Share 링크는 같은 경로를 탄다.

```
파일 선택 ─┐                                   ┌─ 실패 → 토스트로 이유 표시, 보드 그대로
           ├→ parseBoardJson ─→ confirm(요약) ─┤
#data= 링크 ┘  (크기·JSON·app·버전·형태 검사    └─ 확인 → 현재 보드 백업 → 교체 → 저장
               + normalizeState)                         (백업/저장 실패 시 원상 복구)
```

| 기능 | 내용 |
|---|---|
| **Export** | `{app:"team-brawl", schemaVersion:3, exportedAt, ...board}` 를 보기 좋게(2칸 들여쓰기) 저장. 파일명 `team-brawl-board-YYYY-MM-DD.json`. object URL 을 해제(revoke)한다 |
| **Import** | 헤더 `Import` → 파일 선택 → 검증 → 확인창(맵·역할·노트 수, 내보낸 시각, 건너뛴 항목) → 교체 |
| **Undo import** | 교체 직전 보드를 `team-brawl-v2:import-backup` 에 1단계 보관. 백업이 있을 때만 버튼이 보이고, 누르면 확인 후 복원하고 백업을 지운다 |
| **Share 링크 열기** | 페이지 로드 시와 `hashchange` 때 `#data=` 를 읽는다. 해시는 **확인창을 띄우기 전에 지운다** — 새로고침해도 다시 묻지 않게 |
| **Share 링크 만들기** | base64url(`-` `_`, 패딩 없음) 로 변경. 메신저가 `+ / =` 를 바꿔도 안전. 링크 길이를 안내한다. `file://` 로 열었으면 "이 컴퓨터에서만 열린다"고 경고 |
| **링크 복사** | 클립보드 실패 시 텍스트를 선택해 두고 Ctrl+C 를 안내 (기존엔 실패해도 "copied!") |

**호환성**: 버전 필드가 없는 **이전 Export 파일**과 **이전 Share 링크**(표준 base64, `btoa(unescape(encodeURIComponent()))`)를 그대로 연다. 테스트로 고정.

## C. Critical Path — 데이터 정합성 · 보안

### C-1. 교체 순서가 곧 안전장치다 (`replaceBoard`) — 리뷰 후 수정됨
1. **현재 보드를 먼저 저장** (`persist()`, 대기 중인 노트 포함) → 성공 여부 `currentSaved` 기억
2. 기존 백업 원문을 읽어 둔다 (`readBackupRaw`)
3. **백업 쓰기** → 실패하면 두 번째 확인창: "백업할 수 없어 되돌릴 수 없다. 그래도 교체?" (저장소 차단·가득 참)
4. 메모리 교체 → roster 대조 → **저장**
   - 실패 → 메모리를 이전 보드로, **2에서 읽은 백업을 그대로 되돌려 씀**, `currentSaved` 면 배너 해제
   - 단, 저장소가 *차단(unavailable)* 된 브라우저는 원래 아무것도 저장되지 않으므로 메모리에서만 교체하고 진행. 이 경우 첫 확인창이 처음부터 "되돌릴 수 없다"고 말하고 두 번째 확인창은 생략
   - 백업 없이(3에서 동의) 교체에 성공하면 **남아 있던 예전 백업을 지운다** — 안 지우면 'Undo import' 가 두 번 전 보드를 되살린다(2차 리뷰)

이 순서를 바꾸면 "백업 없이 덮어쓴" 상태나 "실패했는데 Undo 지점이 사라진" 상태가 생긴다.
- ⚠️ 백업은 **1단계**다. Import 를 *성공적으로* 두 번 하면 첫 Import 이전 보드는 사라진다.
- 리뷰 전에는 4의 실패 경로가 백업을 **삭제**해서, 실패한 Import 가 이전 Import 의 Undo 지점을 지웠다(TB-3). 수정 후 브라우저에서 재현 테스트로 확인.

### C-2. 외부 데이터는 전부 `normalizeState` 를 거친다
- **XSS**: 역할 색상은 `#rrggbb` 만 통과, 나머지는 기본색 + 경고. 렌더도 DOM API 로 바꿔 이중 방어(P1). 이름·노트는 모두 `textContent`/`value`/`confirm()` 텍스트로만 들어간다.
- **프로토타입 오염**: 모든 사전(dict)에서 `__proto__` 키를 버린다. 맵 이름 `__proto__` 도 버린다.
- **용량**: 텍스트 **2,000,000자** 상한(`MAX_TRANSFER_CHARS`). 파일은 읽기 전에 바이트 크기로 1차 차단, 링크는 디코딩 전에 길이로 1차 차단. 상한 근거: localStorage ~5MB 를 *현재 보드 + 백업 + 새 보드*가 나눠 쓰고, GitHub Pages 계정의 다른 프로젝트와도 공유한다. 실제 보드는 ~50KB. → **임의로 정한 값**이니 바꿔도 된다.
- **확인 없이 교체 불가**: 링크든 파일이든 `confirm()` 을 통과해야 한다. 악의적 링크가 몰래 보드를 갈아치우는 경로는 없다.
- **크기 상한만으로는 부족했다 (리뷰 TB-1·TB-2)**: 2M자 안에서도
  - 맵 2만 개짜리 보드는 Import 후 `reconcileWithRoster` 가 모든 맵에 브롤러를 채우면서 **약 100배(수천만 자)로 불어나** 멈추거나 저장에 실패했다. 처음 방문한 팀원은 roster 가 늦게 도착해 *Import 는 성공했는데 이후 저장이 영원히 실패*하는 상태가 됐다.
  - 역할 1만 개 × 브롤러당 1000개 지정은 렌더마다 `find()` 를 곱으로 돌려 **새로고침할 때마다 수 초~수십 초 멈췄다.**
  - 수정: 외부 데이터에만 **맵 ≤ 200, 역할 ≤ 200** (`MAX_IMPORT_MAPS/ROLES`, 임의값) + 렌더의 역할 조회를 `Map` 으로(200 역할 × 1000 지정에서 11ms). 자기 저장 데이터에는 상한 없음(무손실 불변식 유지).
  - 2차 리뷰: 맵 수를 막아도 **한 티어 표에 가짜 브롤러 키 2만 개**를 넣으면 사용자가 맵을 열거나 추가할 때마다 그 표가 복사되어 19번째 맵에서 저장이 영구 실패했다. 이름 하나를 수백만 자로 만들어도 비슷했다. → 브롤러 키를 담는 모든 표·목록 **≤ 1000개**, 맵·역할·브롤러 이름 **≤ 100자** (`MAX_IMPORT_BRAWLERS`, `MAX_IMPORT_NAME_LENGTH`, 임의값. 실제 roster 는 ~110명).
- **내보낸 것이 다시 들어오는지 즉시 확인**: Export/Share 가 생성 직후 같은 검증기(`parseBoardJson`/`decodeShareHash`)로 자기 출력을 검사해, 다시 Import 할 수 없으면 바로 경고한다. 들여쓰기 때문에 상한을 넘으면 compact JSON 으로 저장.

### C-3. 버전 정책
| 들어온 데이터 | localStorage (자기 데이터) | Import / 링크 (외부) |
|---|---|---|
| 버전 없음 | v2 로 간주, 로드 | v2 로 간주, 허용 |
| 2, 3 | 로드 | 허용 |
| 4 이상 (신버전) | 원본 격리 후 이해하는 부분만 로드 | **거부** — "페이지를 새로고침해 업데이트" |
| 정수가 아님 | 손상으로 격리 | 거부 |

### C-4. ⚠️ Share 링크 + 여러 탭 = 조용한 덮어쓰기 (P1 C-4 의 구체적 시나리오)
팀원이 보드를 연 탭을 둔 채 메신저에서 Share 링크를 클릭 → 새 탭에서 Import 성공 → **기존 탭**에서 드래그 한 번 → 기존 탭의 오래된 state 가 전체 저장되어 **방금 Import 한 보드가 사라진다.** (백업에는 Import 이전 보드가 있으므로 Undo 로도 못 살린다.)
탭 간 동기화는 제외하기로 했지만, 이 흐름은 Share 기능 때문에 자주 생긴다. **`storage` 이벤트로 "다른 탭에서 보드가 바뀜 — 새로고침" 배너 + 그 탭 저장 중지**를 다음 작업으로 권한다.

### C-5. 리뷰에서 함께 고친 기존 결함 (Import 가 노출시킨 것)
- 관리 모달이 열린 채 Share 링크로 보드가 바뀌면, 모달의 Rename/Delete 가 **새 보드의 엉뚱한 맵·역할을 수정**했다 → 교체 시 모달을 닫는다.
- 메모·링크 등 아무 텍스트를 티어에 드롭하면 **가짜 브롤러 키가 영구 저장**되고 Export/링크로 퍼졌다 → roster 에 있는 이름만 허용.
- 역할 삭제 후 지정 패널에 버튼이 남아, 누르면 지운 역할이 다시 저장됐다 → `renderAll` 이 패널도 다시 그림.
- 저장 정지(`saveBlocked`) 상태에서 배너를 닫으면 이후 저장 실패가 조용했다 → 실패할 때마다 다시 표시.
- (P1 관련) 오프라인 + roster 캐시 없음 + 레거시 `placements` 만 있는 데이터에서 레거시 티어가 지워졌다 → All Maps 시딩을 roster 확인보다 먼저.

### C-6. 처음 방문한 팀원
저장된 보드가 없는 팀원이 링크를 열어도 "현재 보드를 백업한다"는 확인창이 뜨고, 이후 'Undo import' 버튼이 생긴다(빈 기본 보드로 되돌림). 해롭지 않지만 어색할 수 있다.

## D. 새로 도입한 것

| 무엇 | 설명 |
|---|---|
| base64url 공유 형식 | 새 링크는 `-` `_` 사용·패딩 없음. 디코더는 표준 base64, 공백(+ 변형), 퍼센트 인코딩까지 수용 |
| `TextEncoder`/`TextDecoder({fatal:true})` | 폐기 예정인 `escape/unescape` 대체. 깨진 UTF-8 은 조용히 깨진 글자가 아니라 오류로 처리 |
| localStorage 키 `team-brawl-v2:import-backup` | `{savedAt, source:"file"\|"link", board}` |
| Export 메타 필드 | `app`, `schemaVersion`, `exportedAt` (최상위, 보드 필드와 같은 레벨 — 구버전 코드가 읽어도 무시됨) |
| 외부 데이터 상한 | `MAX_TRANSFER_CHARS=2,000,000`, `MAX_IMPORT_MAPS=200`, `MAX_IMPORT_ROLES=200`, `MAX_IMPORT_BRAWLERS=1000`, `MAX_IMPORT_NAME_LENGTH=100` — **모두 임의로 정한 값** (근거는 C-2). 오류 코드 `too-large`/`too-many`/`too-long` |
| `store.readBackupRaw()` / `writeBackupRaw(raw)` | 실패한 Import 가 덮어쓴 백업을 원문 그대로 되돌리기 위한 저수준 API |
